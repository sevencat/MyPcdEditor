### 2026-11-21 M4 多包合并（Debug，两套真实样例）

对象：`180314`（16.19 M 点）作参考包，`210819`（32.46 M 点）作待合并包，`MapMerger.Merge` 全流程计时。
ICP 采样后实际参与配准的点：源 249,261 / 目标 1,951,000（源点数按 250 k 上限均匀抽样）。

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 锚点初值 → 首次对应点 RMSE | — | 平移 (−191.844, −66.500, −0.199)，RMSE 0.548 m |
| ICP 两级配准 | 17.7 s | 修正 0.10 m / yaw −0.002°，RMSE 0.548 → 0.113 m，9 轮收敛 |
| 点云合并（不去重） | 36.0 s | 16.19 M + 32.46 M → 48,654,696 点 |
| 点云合并（去重 0.05 m） | 78.7 s | → 45,471,398 点（93.5%，重叠面上压掉 3.18 M 重复点） |
| 栅格合并 | 12.1 s | 7047×6353 @0.1 m/px，44.7 M px |
| 导出成完整包 | 0.4 s | `jueying.pcd`(584 MB) + pgm + yaml + `.projected_origin` + toml |
| 替换原包（同目录副本） | 0.3 s | 5 个文件先让位 `.bak` 再就位；pcd 48,654,696 点，备份 16,193,746 点 |
| 框选删除（屏幕矩形，Release） | 0.48 s | 48,654,696 点框掉中间 40%×40% → 删 23,765,391、剩 24,889,305（Debug 同操作 5.4 s，是没内联的 `Vector4.Transform` 拖慢的） |
| 笔刷擦除（40 段笔迹，Release） | 0.89 s | 48,654,696 点沿屏幕中间横线擦掉 3,320,304 → 剩 45,334,392；每点要遍历 40 段折线，比框选慢约 1.9 倍 |

导出的 0.4 s 是「写 `.tmp` + 同目录改名」，数字偏快是因为 584 MB 落在页缓存里、改名只是元数据操作；
换到机械盘或写满缓存时会退回接近写盘带宽的量级。重新 `MapPackage.Open` 读回校验：48,654,696 点，
锚点 (342607.958, 3432976.777, 14.063) zone 21，yaml 0.1 m/px。

栅格合并结果分布：占用 394 k px / 空闲 43.7 M px / 未知 667 k px，其中 19.3 M px（43%）被两包同时覆盖。

降采样体素对解的影响（同一份数据只改 `TargetVoxelSize`）：

| 目标体素 | 解 X | 解 Y | 最终 RMSE | 内点率 |
|---|---|---|---|---|
| 0.10 m | −191.837 | −66.503 | 0.113 m | 20.4% |
| 0.25 m（默认） | −191.880 | −66.498 | 0.113 m | 20.4% |
| 0.50 m | −191.967 | −66.560 | 0.113 m | 20.4% |

三档之间只差 1~13 cm，量级与 ICP 自身的采样噪声相当 → 这两包的**锚点本身已经足够准**，
ICP 的 0.10 m 修正更接近「确认 + 微调」，而不是纠正建图漂移。内点率 20.4% 低是几何事实：
待合包覆盖面积约为参考包两倍，重叠区只占源点的一小部分（判据见 ADR-017）。

去重的性价比：0.05 m 去重多花 42 s（36 → 79 s）只压掉 6.5% 的点，但去的是**重叠面上成对重复的表面点**
（两趟扫描采样同一面墙），对后续渲染与再合成的价值高于点数比例本身；所以保持默认开启，界面上可填 0 关掉。

### 2026-11-21 M3 优化算子（Release，8 核）

两套样例数据，Release 构建，单进程串行跑（`XyzCloud.Open` 零拷贝读入后逐个算子计时）：

| 算子 | 210819（32.46 M 点） | 180314（16.19 M 点） |
|---|---|---|
| 体素降采样 0.05 m | 32,460,950 → 30,421,471（保留 93.7%）· 6795 ms | 16,193,746 → 15,969,118（98.6%）· 3788 ms |
| 体素降采样 0.10 m | → 16,496,788（50.8%）· 7561 ms | → 8,796,776（54.3%）· 3281 ms |
| 体素降采样 0.20 m | → 5,410,519（16.7%）· 5118 ms | → 2,869,945（17.7%）· 2691 ms |
| Box 裁剪（保留中央 50%×50%） | → 2,386,584（7.4%）· 334 ms | → 2,140,960（13.2%）· 226 ms |
| Box 裁剪（剔除中央） | → 30,074,366 · 1035 ms | → 14,052,786 · 335 ms |
| SOR k=8 σ×1.0 @0.20 m | 5,410,519 → 5,047,517（删 6.7%）· 7824 ms | 2,869,945 → 2,702,222（删 5.8%）· 4774 ms |
| SOR k=16 σ×1.0 @0.20 m | → 5,046,588（删 6.7%）· 14348 ms | → 2,693,300（删 6.2%）· 7091 ms |
| 去毛刺（8 邻域 ≤1） | 6894×4751，改 12,595 px（0.038%）· 393 ms | 6811×4503，改 8,648 px（0.028%）· 182 ms |
| 补洞（闭运算 r=1） | 改 48,502 px · 1149 ms | 改 22,823 px · 894 ms |
| 去孤岛（≥16 px） | 删 8775 块 / 25,700 px · 192 ms | 删 6238 块 / 18,224 px · 179 ms |
| 去孤岛（≥256 px） | 删 9999 块 / 95,689 px · 178 ms | 删 7033 块 / 64,225 px · 170 ms |
| 导出（0.20 m 结果 → binary pcd） | 5.41 M 点 → 61.9 MB | 2.87 M 点 → 32.8 MB |

裁剪取的点数对得上：保留 + 剔除 = 源点数（32,460,950 / 16,193,746，逐点核对过，Box 边界不漏不重）。
SOR 的 k=8 与 k=16 在两套数据上删除比例几乎相同（6~7%），说明这两套图的离群点以「明显偏离」为主，与 k 取值不敏感。

踩到的两个坑（已修，都是本次新代码里 O(n²) 级退化）：

1. **体素哈希只留 24 位**：表按 `hash & (capacity-1)` 取槽，32 M 点时容量涨到 2^26，
   高 48 M 个槽永远空着、低 16 M 个槽挤爆 → 0.05 m 降采样跑 90 s 还没完。改成 32 位全值域后 6.8 s。
   已加回归测试 `VoxelHash_SpreadsAcrossFullIntRange`。
2. **SOR 网格按包围盒体积估格子**：705×493×37 m 的空心场景被估成 1.3 点/m³、格子边长 2.3 m，
   每格上千点，16.5 M 点 SOR 跑 140 s 仍未完成。改按包围盒**表面积**估（21 点/m² → 0.22 m 间距），
   并让近邻网格按实际占用格数扩容；查询阶段并行化。5.4 M 点 k=8：71.6 s → **7.5 s**。

结论：点云算子里体素降采样是「全云一遍」，0.05 m 也要 5~7 s，UI 里必须给进度条（已有）；
SOR 是唯一的重算子，10 M 点以上提示先降采样。

### 2026-11-20 M0+M1+基础 3D 查看（首次基线）

窗口 2380×1312（DPI 1.75），Debug 构建，`PGV_TRACE_FPS=1` 采样：

| 指标 | 180314 (16.19 M) | 210819 (32.46 M) |
|---|---|---|
| 打开→首帧可见（s） | ~1.3 | ~1.8 |
| PCD 读取（含包围盒抽样） | 169 ms（零拷贝） | ~400 ms（零拷贝） |
| 点云上传（MMF → VBO，64 MB/片） | 3 片，~0.7 s | 6 片，~1.5 s |
| 稳态 FPS（静止，相机固定） | 30–31 | 20 |
| 首帧后 2 s 内 FPS（上传刚结束） | 18.4 | 6.8 → 17.7 |
| 显存（VBO，12 B/点） | 194 MB | 390 MB |
| 托管堆峰值 | 未测（零拷贝路径不建点数组） | 同左 |

观察：

1. **FPS 与点数近似线性**（16 M→30 fps，32 M→20 fps），瓶颈是每帧 3200 万个顶点的提交与像素填充，不是 IO。
2. 上传期间 FPS 掉到 5–7，原因是每片 `BufferSubData` 64 MB 占满一帧；分片大小与「每帧允许的上传字节数」需要解耦（当前是一帧一片）。
3. 零拷贝路径生效：371 MB 的 PCD 没有额外 371 MB 托管数组，加载仅 ~400 ms。
4. 若后续要更高帧率，优先做**索引抽样绘制**（按 1/2、1/4 抽稀，`glDrawElements`）或分块 + 视锥剔除，而不是继续抠着色器。

### 2026-11-20 M2d 点云抽样降载（索引抽样）

先归因：`PGV_NO_MAP=1` 收起 2D 面板后 GL 视口 1424×1312 → 2380×1312（面积 +67%），
32.46 M 数据帧率 17.0 → 17.1，**不随分辨率变化**，确认瓶颈是顶点提交而非填充。

实测（窗口 1424×1312，2D 面板 + 地面纹理全开，Debug，稳态中位数）：

| 数据集 | 全部 | 1/2 | 1/4 | 1/8 |
|---|---|---|---|---|
| 16.19 M `180314` | 31.0 | 49.6 | 63.0 | 62.4 |
| 32.46 M `210819` | 17.7 | 31.0 | 43.0 | 60.0 |

（同一数据在收起 2D 面板、2380×1312 下：1/2 = 30.0、1/4 = 40.3、1/8 = 55.5 —— 与上表同量级，
进一步说明分辨率不起作用。）

结论：

1. **帧率与顶点数近似线性**，1/8 档 60~63 FPS 已经撞上帧泵上限（16 M 的 1/4 也只有 63），
   再抽不会更快。
2. 索引抽样的跨步访问没有带宽惩罚：同一档位下与"只画前 1/N 个点"的前缀截断帧率完全一致
   （都是 40.3），所以选了空间全覆盖的索引方案。
3. 索引缓冲成本：1/4 档 32.46 M/4 = 8.1 M 个 uint = 32 MB，重建 ~20 ms（仅切档时）。
4. 全量 32 M 若还要更快，只剩"分块 + 视锥剔除"一条路（少画视野外的块），与抽样正交。

### 2026-11-20 M2e 分块 + 视锥剔除（连续区间分块）

改动：点序按 **连续点区间** 切块（默认 64 K 点/块，32.46 M 切 496 块，`PGV_CHUNK_POINTS` 可覆盖），
每块一个 AABB；每帧从 view-projection 提 6 个平面（Gribb–Hartmann）做 p-vertex 保守测试，
只 `DrawElements`/`DrawArrays` 通过测试的块。抽样索引仍按升序生成（第 k 个索引 = k·step），
所以一块天然对应索引缓冲里一段连续区间，块与抽样正交、**不需要为每块单独建索引**。

放大到局部的 A/B 用 `PGV_CAM_ZOOM=0.08`（`Fit` 后把相机距离乘 0.08）、`PGV_NO_CULL=1` 关剔除。

实测（窗口 2380×1312 = `PGV_NO_MAP=1`，Debug，稳态中位数；两次复测并列）：

| 场景 | 剔除关 | 剔除开 |
|---|---|---|
| 32.46 M 全图（496 块全可见） | 16.8 | 17.4 / 17.5 |
| 32.46 M `zoom 0.08` | 19.7 | 32.7 / 34.4 |
| 32.46 M `zoom 0.25` | 8.6 | 9.4 |
| 16.19 M 全图 | 30.7 | 31.7 |
| 32.46 M 全图 · 单块（`PGV_CHUNK_POINTS=33554432`） | 16.4 | — |
| 32.46 M `zoom 0.08` + 1/4 抽样 | — | 54.0 |

加载与本轮扫描（`--selftest` 顺带打印）：

| 指标 | 180314 (16.19 M) | 210819 (32.46 M) |
|---|---|---|
| GPU 上传完成（elapsed，含读取） | 1628 ms | 5077~5562 ms |
| 后台分块扫描（与上传并行） | 1054 ms | 1406~1911 ms |
| selftest 总计 / 均值 FPS | 2170 ms / 6.9 | 5833~6350 ms / 15.6 |

结论：

1. **全图视角不划算、也不需要**：496 块全可见时只比单块多 1.0 FPS（17.4 vs 16.4），
   496 次 draw call 在 ANGLE 上没有可测开销；全图本来就没有视野外的点可省。
2. **放大到局部是主要收益**：`zoom 0.08` 只提交 11.10 M/32.46 M 点（34.2%）→ 19.7 → 33~34 FPS（约 1.7×）。
   与 1/4 抽样叠加到 54 FPS（2.8 M 点），两条正交手段可以同时用。
3. **正确性对拍通过**：`zoom 0.08` 剔除开/关两帧像素统计完全一致
   （非背景 100.0%、唯一色 132、平均亮度 68.5、彩色 6.6%），即没有误剔可见块。
4. **分块粒度取决于点序的空间局部性**：这份数据 4 K 点就横跨 132 m，块对角线平均 188~200 m
   （全图 857~862 m）。原来的 512 K 点/块（放大只省 18% 的点）不够用，64 K 才省 66%，
   所以定 64 K；更小（4 K）块数上万、draw call 开始有成本，收益却递减。
5. **必须后台扫**：整云扫描 Debug 下 1.4~1.9 s。塞进上传泵（每片 64 MB 后同步扫）会把加载
   从 5.5 s 拖到 7.2 s；改成后台 `Task` 与 GL 上传并行后总耗时回到 5.8~6.4 s（32 M）/2.2 s（16 M）。
   代价是后台线程与上传抢核，扫描本身和上传都会慢几百毫秒——但墙钟仍净下降。
   换图/关闭窗口时必须**取消并等待**该任务再 `Dispose` 云数据（它读的是映射内存）。
6. 本轮全图数值（17.4）低于上一轮记录的 19.0~19.5，同一轮的单块对照也只有 16.4，
   说明是机器状态漂移（与下一条 M2c 记录里的同类现象一致），不是本次改动引入的回归；
   横向比较同一轮内的开/关数值才是有效结论。

#### Release 复核（2026-11-21）

`dotnet build -c Release` 后重跑同样的 A/B（脚本同参数，只是 exe 换成 `bin/Release/net11.0/win-x64`）：

| 场景 | 剔除关 | 剔除开 |
|---|---|---|
| 32.46 M 全图 | 16.8 | 16.7 |
| 32.46 M `zoom 0.08` | 17.7 | 29.5 |
| 32.46 M `zoom 0.25` | 8.4 | 9.1 |
| 16.19 M 全图 | 29.2 | 29.0 |
| 32.46 M `zoom 0.08` + 1/4 抽样 | — | 47.5（38.6–55.5） |

加载与后台扫描（`--selftest`，Release）：

| 指标 | 180314 (16.19 M) | 210819 (32.46 M) |
|---|---|---|
| GPU 上传完成 | 672 ms | 2247 ms |
| 后台分块扫描 | 56 ms | 132 ms |
| selftest 总计 | 1120 ms | 2902 ms |
| 分块数 | 248 | 496 |

结论：

1. **帧率与构建配置无关**（各场景 Debug/Release 差值在 ±10% 内，`zoom 0.08` 29.5 vs 34.4 属测量抖动），
   再次印证瓶颈是 GPU 顶点提交，CPU 侧（分块测试、draw call 循环）不是瓶颈。
2. **后台扫描在 Release 下只要 132 ms**（Debug 1406~1911 ms，差 11~14 倍）——纯标量循环吃 JIT 质量。
   它已远小于上传的 2.2 s，所以"必须并行"这个约束在 Release 下并不成立；但后台跑仍然是正确选择：
   Debug 开发体验、更慢的机器（GPIO 巡检笔记本）以及以后拆成多线程扫描都不必返工。
3. Release 下打开 32 M 数据 2.9 s、16 M 1.1 s，比 Debug 快一倍，主要省在文件读取与扫描。

### 2026-11-20 M2c 地面纹理（PGM 贴到 3D 地面）

改动：加载时把 PGM 按整数块 max-pooling 降到 ≤2048 边长（`GroundTexture.Build`，块 4），
再作为单个 RGBA8 纹理铺在点云下方的一个四边形上。测量方式：`PGV_TRACE_FPS=1` 打开窗口，
采样 20 s，丢掉前 1/3 预热段取中位数；A/B 用 `PGV_NO_GROUND=1` 关掉地面纹理。
窗口 1424×1312（2D 面板占 2/5），Debug。

| 指标 | 180314 (16.19 M) | 210819 (32.46 M) |
|---|---|---|
| 地面纹理构建（CPU，后台线程） | 215 ms（6811×4503 → 1703×1126） | 224 ms（6894×4751 → 1724×1188） |
| 纹理显存（RGBA8） | 7.7 MB | 8.2 MB |
| 墙 texel 占比（膨胀半径 2 后） | 6.8% | 9.3% |
| 稳态 FPS（地面开） | 31.5（30.0–34.1） | 17.0（16.2–18.0） |
| 稳态 FPS（地面关） | 33.0（噪声大，10–37.7） | 17.0（16.7–17.1） |

结论：

1. **地面纹理对帧率无可测影响**——只是 1 个四边形（2 个三角形）+ 一张 8 MB 纹理，
   填充成本被 3000 万点的绘制完全掩盖（32 M 数据开/关中位数都是 17.0）。
2. 构建 215 ms 在后台 `Task.Run` 里跑（与 PGM 读取、点云打开同一批），不阻塞 UI；
   单次加载额外的墙钟开销可忽略（16 M 数据总开销 1.44 s vs 基线 ~1.3 s，其中含 2D 面板）。
3. 显存 +8 MB 相对点云 VBO（194/390 MB）是零头，不需要分块或按需上传，也就不用 LOD。
4. 32 M 数据本轮 17 FPS 低于首轮基线的 20 FPS，但同一次测量的「地面关」也是 17 FPS，
   说明与地面纹理无关。M2d 又用 `PGV_NO_MAP=1` 排除了 2D 面板，仍为 17.1，
   因此这 3 FPS 的差异属于测量环境变化（首轮基线与本轮的机器状态/窗口不同），
   不是某个改动引入的回归。
